# Decisions and verified assumptions

Decisions made without asking, as section 2 of the engineering brief (2026-10-28) allows. Each entry gives one line of reasoning. Newest entries are at the bottom of each section.

## Phase 0: Neon port

| #   | Decision                                                                                                                                                                                                                         | Reasoning                                                                                                                                                                                                                                                                                                              |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | Owners live in `public.owners(auth_provider, auth_subject)`, and ledger foreign keys reference that table instead of Neon Auth's user table.                                                                                     | The ledger does not depend on Neon Auth's internal schema, and the same owner row can later be reached through MCP OAuth.                                                                                                                                                                                              |
| D2  | Identity is the transaction-local setting `app.owner_id`, set with `set_config(..., true)` inside each request transaction.                                                                                                      | Transaction-local settings are discarded at commit, so a pooled connection cannot carry one owner's identity into another request. A test covers this.                                                                                                                                                                 |
| D3  | The app connects as a separate login role, `perkkeep_app` (no `BYPASSRLS`, no superuser, owns nothing), through `PERKKEEP_DATABASE_URL`. Each pool checks those three properties on first use and refuses to serve if any fails. | Brief section 4 forbids serving user queries under the owner role. A separate login role is stronger than `SET ROLE`, which a later `RESET ROLE` can undo.                                                                                                                                                             |
| D4  | Every ledger table uses `FORCE ROW LEVEL SECURITY`.                                                                                                                                                                              | A future table owner without `BYPASSRLS` would otherwise skip the policies silently.                                                                                                                                                                                                                                   |
| D5  | The browser calls a fixed list of named operations (`/api/ledger`). It never sends SQL, table names, or column lists. Evidence entered in the app is always recorded as `recorded_by = 'user'`.                                  | This keeps the attack surface small and stops a client from forging import or inference provenance.                                                                                                                                                                                                                    |
| D6  | Sessions are verified on the server with Neon Auth `getSession()`, with the signed session-data cookie cache set to 60 seconds (the default is 300).                                                                             | This shortens the window in which a revoked session still opens the ledger, at the cost of more upstream session checks.                                                                                                                                                                                               |
| D7  | Access requires a verified email address that appears in `PERKKEEP_OWNER_EMAILS`. An empty list admits nobody.                                                                                                                   | This gives "private owner access only" that fails closed, whatever sign-up settings Neon Auth has.                                                                                                                                                                                                                     |
| D8  | State-changing routes require an `Origin` in the allowed list (Vercel system URLs plus `PERKKEEP_ALLOWED_ORIGINS`) and `Sec-Fetch-Site: same-origin` when the browser sends it.                                                  | Cookie-authenticated routes need cross-site request protection.                                                                                                                                                                                                                                                        |
| D9  | A synthetic test identity provider exists for local tests only. It turns off on Vercel and with a non-local database, and the build guard rejects it.                                                                            | Neon Auth sets `__Secure-` cookies and calls a hosted service, so local browser tests cannot use it.                                                                                                                                                                                                                   |
| D10 | Migrations run manually (`npm run db:migrate`, `npm run neon:provision`) over the direct (unpooled) connection, never during a Vercel build.                                                                                     | A preview build must not change the production schema, and session advisory locks need a direct connection.                                                                                                                                                                                                            |
| D11 | Neon is the only database. All Supabase code, migrations, scripts, types and dependencies were removed.                                                                                                                          | Owner instruction (2026-10-28), after the ported suite passed on PostgreSQL. The earlier local Supabase stack's data, if any, stays wherever that stack stored it on the owner's Mac; it was never migrated.                                                                                                           |
| D12 | The snapshot API returns the newest 1,000 audit events.                                                                                                                                                                          | All audit rows stay in the database, and the cap keeps the 60-second refresh bounded as history grows.                                                                                                                                                                                                                 |
| D13 | The seven low-severity audit findings are left in place.                                                                                                                                                                         | All seven trace to one advisory (GHSA-gcqx-w48m-w2h4, `deepmerge`) reached through `@neondatabase/auth-ui` email rendering. PerkKeep imports none of these packages, the built `.next` output contains none of their code, and the only fix is a semver-major change.                                                  |
| D14 | The SimpleFIN setup token was not claimed from the cloud agent container.                                                                                                                                                        | A setup token can be claimed only once ([SimpleFIN developer guide](https://beta-bridge.simplefin.org/info/developers)), the container is temporary, and the brief does not name the container as a destination for real financial data. The token belongs in the owner-only settings page once that page is deployed. |
| D15 | Card art (section 8a) will be stored in Neon as owner-scoped bytes under the same row-level security, and served with `no-store`.                                                                                                | Neon is already private infrastructure named in the brief, so no extra storage service or plan is needed.                                                                                                                                                                                                              |
| D16 | `neon:provision --vercel` writes production variables only.                                                                                                                                                                      | `vercel env add` for preview can ask which branch to target. Preview builds fail closed at the guard until preview variables exist.                                                                                                                                                                                    |
| D17 | Generated database passwords use 192 random bits plus fixed character classes.                                                                                                                                                   | Neon's role documentation asks for mixed character classes in SQL-set passwords.                                                                                                                                                                                                                                       |

## Phase 1: sources, and section 8a: card art

| #   | Decision                                                                                                                                                                                                                                                                                                                                                 | Reasoning                                                                                                                                                                                                          |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| D18 | Accounts and transactions store keyed digests (HMAC-SHA-256) of source identifiers, never the raw ids. The digest key is derived from `PERKKEEP_ENCRYPTION_KEY` with HKDF.                                                                                                                                                                               | Brief section 5 forbids storing raw source payloads. Rotating that key will need a re-keying migration, which is recorded here so it is not done casually.                                                         |
| D19 | Transactions form one linear revision chain per source reference (`observed`, then `revised` or `removed`). For SimpleFIN, which reports no removals, a pending charge that disappears from a window the source returned in full is recorded as `removed`. Posted charges are never inferred as removed.                                                 | Brief section 5 requires pending-to-posted changes and removals to be linked corrections, never deletions. A pending charge replaced by a posted one under a new id is the common case.                            |
| D20 | Each sync requests at most 90 days, including today (SimpleFIN's per-request limit). Later syncs overlap the last success by 14 days. Coverage starts at the requested window and ends at the source's own last refresh date (`balance-date`), not the day the sync ran.                                                                                 | SimpleFIN refreshes about once a day, so "synced today" would overstate coverage. SimpleFIN may return less history than requested, so the UI labels coverage as the requested window.                             |
| D21 | CSV files import only into CSV accounts. Deduplication between a CSV account and an aggregator account for the same card is deferred to the Phase 2 matchers.                                                                                                                                                                                            | Rows from different sources have no shared identifier, so merging them safely needs matching logic, not a database key.                                                                                            |
| D22 | A CSV import's idempotency key is the file's SHA-256. A digest of the target account, format and parsed rows detects a replay of the same file with different settings, which is rejected.                                                                                                                                                               | This implements "replaying the same file creates nothing new; a different file with the same key is rejected" (brief section 5).                                                                                   |
| D23 | When two layouts share the same columns (Amex and generic `Date, Description, Amount`), the owner must choose the layout, because the sign conventions differ. Issuer layouts are labeled unverified until a real file of each kind has imported correctly. Copilot Money is unsupported until a sample exists.                                          | A wrong sign would turn every purchase into a credit.                                                                                                                                                              |
| D24 | Mapping is proposed only when the institution matches the card's issuer and exactly one card has the same last four digits. The owner confirms every link, and the unidentified Chase record is never assumed to be an Ink card.                                                                                                                         | Brief section 5.                                                                                                                                                                                                   |
| D25 | Daily sync runs at 10:23 UTC (`vercel.json`). The cron route requires `CRON_SECRET` and returns counts only.                                                                                                                                                                                                                                             | Hobby allows one run per day (see the section 14 table).                                                                                                                                                           |
| D26 | The Plaid adapter calls Sandbox only and refuses any other `PLAID_ENV`. It has not run against Plaid.                                                                                                                                                                                                                                                    | Brief section 5. No Plaid credentials are available here.                                                                                                                                                          |
| D27 | Card art is stored in Neon (`card_art`, owner-scoped bytes under row-level security), normalized with `sharp` to 1012×638 WebP (1.586:1), and served only by an authenticated route with `Cache-Control: private, no-store`.                                                                                                                             | Brief section 8a allows private storage on Neon, which needs no new service or plan.                                                                                                                               |
| D28 | The server fetches issuer art only from URLs listed in `data/card-faces.json`, never from a URL in the request. Images with a baked-in "No annual fee" badge (Freedom Unlimited, both Prime Visa variants found) and Discover's only image (it includes a drop shadow) were not used; those cards keep the placeholder until the owner uploads an image. | Brief section 8a forbids images that include a badge. The listed URLs were found by inspecting each product page's network requests on 2026-10-28.                                                                 |
| D29 | Bands in each card's sampled color cover sample names baked into issuer images ("C F FROST", "D. BARRETT", "BARRETT CONNECT"), and on Gold also the sample "7997" and "09".                                                                                                                                                                              | The owner's name and last four are drawn in those places instead (brief section 8a).                                                                                                                               |
| D30 | The overlay name is the owner's Neon Auth profile name. Account creation asks for it, and Settings can change it.                                                                                                                                                                                                                                        | Brief section 8a: pulled from the profile, never hard-coded.                                                                                                                                                       |
| D31 | Three badge text colors were darkened (to contrast ratios of 5.4 to 5.8).                                                                                                                                                                                                                                                                                | The Settings accessibility audit found the earlier amber badge below WCAG AA contrast.                                                                                                                             |
| D32 | The build guard fails every Vercel build on an unsafe setting, but fails only production builds on missing settings. A preview without settings builds and shows the setup screen.                                                                                                                                                                       | The Vercel project builds every pushed branch. A preview with no settings opens no data, and production must never deploy half-configured.                                                                         |
| D33 | A manual "Sync now" is refused for 30 minutes after the connection's last attempt; the daily cron is unaffected.                                                                                                                                                                                                                                         | SimpleFIN expects at most about 24 `/accounts` requests a day and disables access tokens that exceed it by much ([SimpleFIN developer guide](https://beta-bridge.simplefin.org/info/developers), read 2026-10-28). |

## Phase 2: knowledge layer and deterministic matching

| #   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | Reasoning                                                                                                                                                                                                                                                                                                                          |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D34 | Benefit rules live in `data/benefits/*.json`, one file per product. Gold and Sapphire Reserve were read on the issuers' pages on 2026-10-28; the other six products are marked `researched: false` rather than claimed to have no credits.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | Brief section 7. The Sapphire Reserve rules reflect the issuer's current page (annual travel credit by account anniversary, The Edit, Exclusive Tables, StubHub, Peloton, Lyft, DoorDash, Global Entry), which differ from the earlier draft catalog.                                                                              |
| D35 | A benefit created from a rule records `catalog_rule_id` and `catalog_rule_version`, and the matcher's evidence notes name the rule and version.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | Brief section 7 requires showing which rule version produced each balance.                                                                                                                                                                                                                                                         |
| D36 | Statement-credit description patterns start unverified. Until a rule's `patterns_verified` is `true`, matched credits are candidates for review and the period's coverage is capped at partial.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | The real credit descriptions have not yet been seen in the owner's statements. An unverified pattern could miss a credit, and complete coverage would then show a used benefit as available.                                                                                                                                       |
| D37 | A matched credit supersedes one open candidate purchase in the same period, whether that purchase was recorded in this run or an earlier one.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | Brief section 6: never count both a candidate and its confirmed replacement.                                                                                                                                                                                                                                                       |
| D38 | Benefits that a statement cannot show (Uber Cash, Lyft in-app credit, DoorDash promos, hand-entered rules) never receive coverage from transactions.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | Otherwise "no matching credit" would display as "unused".                                                                                                                                                                                                                                                                          |
| D39 | The matcher runs after every sync, after every CSV import, after each account link, and on demand. A matcher failure is rolled back to a savepoint and never undoes the sync.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | Hands-off use, without risking the source data.                                                                                                                                                                                                                                                                                    |
| D40 | `npm run owner:cards` records the owner's cards as confirmed, and links each synced account whose last four digits match exactly one card, also as confirmed. Card details come from the ignored `.local/owner-cards.json`. The script runs as `perkkeep_app` with the owner's identity, so RLS, guards and the audit trail apply.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | The owner supplied their card list and asked for confirmed status (2026-10-28). That instruction is the owner's confirmation of each card and of each digit-matched link. Card digits never enter the public repository. The owner also identified the record ending in the digits the brief mentioned as Chase Ink Business Cash. |
| D41 | Each synced card account becomes one of the owner's cards, linked and confirmed, with no script. An account whose last four digits match exactly one card of the same issuer links to that card. Otherwise the product named in the account fills in that product's starter card, or a new card is created from the issuer, product and digits the source reported. Bank and investment accounts are skipped, and ambiguous digits are left for the owner. Linking also runs when the owner presses "Match transactions now", so it never costs a SimpleFIN request. An unlinked account is never relinked automatically. Once any account is linked, starter cards that nothing has confirmed, linked or given benefits are hidden, not deleted. A linked SimpleFIN connection shows its status in place of the setup-token form. | The owner connected SimpleFIN and expected their cards to follow from it (2026-10-28). Proposals needed digits on the cards first, and the starter cards had none, so nothing linked. The card identity comes from the issuer's own account data, so nothing is invented; the owner can unlink any account.                        |
| D42 | Production is reachable from a cloud container over Neon's HTTPS and WebSocket endpoints (port 443): `npm run neon:https` runs statements and `npm run neon:reconcile` runs the app's own linking and matching code. Both switch to `perkkeep_app` with `set local role` and set the owner's identity, so RLS, guards and audit triggers apply; only `--auth` reads use the owner role, read-only. The owner role was granted SET (not INHERIT) on `perkkeep_app` on 2026-10-28; undo with `revoke perkkeep_app from neondb_owner`. Credentials are pulled from Vercel into the Git-ignored `.local/neon.https.env`. `.claude/settings.json` allows these commands without prompts.                                                                                                                                                | The container cannot reach port 5432, Vercel never returns the sensitive `PERKKEEP_DATABASE_URL`, and the owner approved direct production access and asked not to be prompted again (2026-10-28). Account names from SimpleFIN put the last four digits in parentheses, which the first parser missed.                            |
| D43 | "Add researched benefits" on a confirmed card creates each researched rule it lacks: eligible (the confirmed card plus the issuer's verified terms), enrollment unknown where the issuer requires it, and a January 1 start, marked `default_start_of_year`, where the issuer publishes none. Rules that need the owner's dates (custom windows) and rules that have ended are skipped. The owner's first real statements verified two Sapphire Reserve credit descriptors ("TRAVEL CREDIT $300/YEAR", "SHOPS AT CHASE $250/YEAR"), and The Shops at Chase credit was added from Chase's page. SimpleFIN windows are capped at 45 days after its responses warned above that.                                                                                                                                                      | The owner asked for the setup to be done for them (2026-10-28). Eligibility follows from verified terms on a confirmed card; enrollment and anniversary dates are facts only the owner or issuer has, so they stay unknown until confirmed.                                                                                        |
| D44 | The owner can add a card by hand (Cards, "Add a card") and remove one (card page, "Remove this card"). An added card starts unverified with no catalog key, so the starter-card hiding of D41 does not apply to it. Removing archives the card (`cards.archived_at`): it leaves the overview, card list, review queue and totals, `ensure_period` refuses new periods, and its periods, evidence, account links and audit history stay in History. Settings lists removed cards with Restore. Discover it gets an official face cropped from Discover's design gallery (the teal design); Freedom Unlimited and Prime Visa still have no clean issuer image (their only images carry a printed badge), so they keep the placeholder until the owner uploads a photo.                                                               | The owner could not add or remove a card in the app (2026-10-28). Archiving instead of deleting keeps the ledger's append-only history intact and makes removal reversible. Discover publishes its designs only as one gallery image, so a fixed crop is the cleanest official source.                                             |
| D45 | Alerts are derived from the ledger on every load and never stored. Kinds: card setup, account link, terms changed, allowance needed, possible use, ending soon, re-check terms, sync stale or failing, coverage not fresh, no current period, and the activity kinds used and fully used. Dismissing an alert appends an acknowledgement of its deterministic key; the key changes when the underlying fact changes (a new rule version, a new sync attempt, a new coverage date), so the alert returns on its own. Non-dismissible alerts (setup, allowance, possible use, re-check, no period) clear only by the action they ask for.                                                                                                                                                                                            | An alert computed from the same rows as the balance can never disagree with it, and an append-only acknowledgement table follows the ledger's own rule that nothing is deleted or rewritten.                                                                                                                                       |
| D46 | The overview, card page and review queue show one compact row per benefit window, grouped by reset timeframe (monthly first, then quarterly, half-yearly, calendar year, cardmember year, one-time, custom), soonest-ending first, with group totals. Each row carries a bar of confirmed use (solid) and possible use (hatched) against the allowance, a tick at today, the amounts, time left, the status badge, and only the hint the row needs. The full record (conditions, enrollment, evidence ledger, notes, rule actions) opens under the row. History keeps the full panels. A bar for a period whose coverage is not fresh is drawn muted, and a window with an unknown allowance gets no bar.                                                                                                                          | The owner's feedback on 2026-10-28: one card per period meant too much scrolling, and monthly and half-yearly benefits needed clear organization by time, value and layout.                                                                                                                                                        |
| D47 | Partial use is entered on the row: an amount, a date defaulting to today, and an optional note, saved as the owner's own manual, confirmed evidence with the note "Entered by the owner on the benefit row." when none is given. The full form stays for statement credits, portal confirmations, refunds, reversals and corrections. Enrollment and eligibility are confirmed with one click on the row's hint, and the eligibility confirmation is a new `markEligible` operation. Evidence entered this way keeps `recorded_by = user`, as the server forces.                                                                                                                                                                                                                                                                   | The owner asked why a number could not be entered and why "confirmed enrollment" could not be clicked (2026-10-28). The ledger already supported partial amounts; only the UI demanded a dialog. The database rule that a manual confirmation carries a note is kept, with a default rather than a required field.                 |
| D48 | A period that starts inside a partial rule window (after a terms change or a mid-period start) keeps an unknown allowance until the owner confirms it, once, with a note, up to the full nominal allowance. The confirmation goes through `confirm_period_allowance`, a column grant limited to the two allowance columns, and a trigger that refuses every other allowance change. Full-window periods stay locked to the verified terms, as before.                                                                                                                                                                                                                                                                                                                                                                              | Without this, every terms change left a period in "needs review" with no way out, and brief section 6 forbids prorating but not an owner-confirmed figure.                                                                                                                                                                         |
| D49 | Terms drift is detected by comparing the rule version a benefit recorded (`catalog_rule_version`) with the rule file's current version. A newer version raises "terms changed" with the field-level differences; a rule missing from the files raises "rule file retired"; a rule whose issuer end date has passed raises "issuer ended this benefit". "Keep current terms" acknowledges the alert; "Review and save a new version" opens the version form prefilled from the rule file. "Terms unchanged today" records `last_reverified_at` without a new version, and a benefit not verified or re-checked for 180 days raises "re-check terms". The 180-day interval is a default with no issuer data behind it.                                                                                                               | Brief section 7: rules are versioned, and the app shows which version produced each balance. Publishing a rule-file change is a pull request and a deploy; the app compares on load, so nothing in the ledger changes until the owner acts.                                                                                        |
| D50 | The only stored alert preference is how many days before a window ends the "ending soon" alert starts (`user_settings.alert_lead_days`, default 7, range 1 to 90). Alerts are in-app only, computed on load and shown on the overview, the review queue and a count on the Review tab. Push notifications are not built.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | The Phase 2 gate names expiration alerts in the PWA. Push needs a device subscription table and a scheduled evaluator, and that is a separate decision once in-app alerts have been used.                                                                                                                                          |
| D51 | `npm run neon:migrate` applies `db/migrations` to production over Neon's WebSocket endpoint (port 443) as the database owner, with the same runner and bookkeeping as `db-migrate.mjs` (each file once, in its own transaction, recorded with its SHA-256, a changed applied file refused). It reads the Git-ignored `.local/neon.https.env` and pulls it from Vercel when missing, like `neon:https`. It never prints connection strings.                                                                                                                                                                                                                                                                                                                                                                                         | The owner asked for the Phase 2 branch to be merged without their involvement (2026-10-28). A container cannot reach port 5432, `neon:provision` needs the owner's Mac, and `neon:https` runs only as `perkkeep_app`, which cannot run DDL.                                                                                        |
| D52 | The app tolerates a database that is one migration behind its code. The snapshot reads the alert tables inside a savepoint and falls back to no acknowledgements and default settings when they are missing, naming the pending migration in the top bar; an operation that needs the missing schema answers 409 `migration_pending` instead of a generic failure. Alerts, progress rows and use entry work on the existing tables; dismissing alerts, alert settings, re-verification and allowance confirmation wait for `npm run neon:migrate`.                                                                                                                                                                                                                                                                                 | The owner asked for the Phase 2 branch to be merged now (2026-10-28), and the cloud container's sandbox refuses to run a production migration. Merging deploys production, so the code had to be safe ahead of its migration rather than fail to open the ledger.                                                                  |
